La mayoría de las demos de generación aumentada por recuperación (RAG) se
construyen al revés: conectas un modelo de embeddings y un LLM, obtienes una
respuesta con buena pinta y la publicas. El problema aparece en cuanto alguien
pregunta si la respuesta es *correcta* — no hay ningún número al que apuntar, ni
forma de saber si el siguiente cambio mejoró o empeoró las cosas.

Este sistema invierte ese orden. El dominio es la legislación española — el
**BOE** (*Boletín Oficial del Estado*), un corpus legal actualizado a diario — y
la regla de diseño es simple: **ningún cambio de recuperación o generación se
integra sin una medición antes/después contra un conjunto de evaluación fijo.**
La calidad se trata como un contrato de ingeniería, validado en CI, igual que una
suite de tests.

Este artículo recorre cómo se construye y se defiende ese contrato, etapa a
etapa.

## La forma de la tubería

<Mermaid code={`flowchart TB

  B --> C[Chunks por estructura<br/>uno por artículo]

  C --> E[(Índice híbrido<br/>dense + BM25)]
  Q[Consulta] --> F[Recuperación híbrida<br/>RRF]
  E --> F
  F --> G[Rerank cross-encoder]
  G --> H[Generación anclada<br/>citar-o-rechazar]
  H --> I[Respuesta citada + fuentes]`} />

Dos mitades: un camino **offline** de ingesta que convierte la API del BOE en un
corpus limpio y listo para recuperación, y un camino **online** de consulta que
recupera, reordena y genera. Entre ambos está la pieza que hace que todo sea
fiable — el arnés de evaluación.

## Trocear es una decisión de recuperación, no un detalle de preprocesado

El movimiento por defecto en RAG es cortar los documentos en ventanas de tamaño
fijo (por ejemplo, 1000 caracteres con 150 de solapamiento). Es fácil, y es
incorrecto para texto legal.

Las leyes tienen estructura — *título → capítulo → sección → artículo* — y el
artículo es la unidad natural de significado *y* de cita. Así que el chunker
recorre esa jerarquía y emite **un chunk por artículo**, llevando el contexto
completo como metadatos:

```python
#: Clases que abren un nuevo nivel de encabezado (límite de chunk, reset).
_HIERARCHY_OPENERS = frozenset({_TITULO_NUM, _CAPITULO_NUM, _SECCION})

def consume(self, block: TextBlock) -> None:
    """Enruta un bloque al handler correcto según su clase de estilo."""
    css = block.css_class
    if css in _HIERARCHY_OPENERS:
        self._open_hierarchy(css, block.text)   # flush + reset niveles inferiores
    elif css == _ARTICULO:
        self._open_article(block.text)          # empieza un nuevo chunk
    else:
        self._append_body(block.text)           # crece el chunk actual
```

Dos reglas mantienen el corpus limpio. Los artículos demasiado largos se dividen
en partes numeradas, pero solo cuando un chunk ya contiene su encabezado **más**
un párrafo — para que ningún encabezado quede huérfano en su propio chunk:

```python
over_limit = prospective > self._config.max_chunk_chars
if len(self._current.texts) >= 2 and over_limit:
    self.flush()
    self._current = self._new_pending()
self._current.texts.append(text)
```

Y los fragmentos sueltos más cortos que el mínimo se fusionan de vuelta en el
chunk anterior — pero solo si comparten el mismo ámbito jerárquico, para que
artículos no relacionados nunca se mezclen. La recompensa es que cada chunk
puede construir su propia cita — `Ley 39/2015, Artículo 3` — y enlazar
directamente a boe.es. Esa cita no es cosmética; es lo que hace que una respuesta
sea auditable.

Que esto supere de verdad al enfoque ingenuo es una afirmación a la que volveré
y *mediré*, no que daré por sentada.

## Las métricas primero: el contrato al que se somete cada cambio

Antes de cualquier ajuste de modelo, el arnés define cómo se puntúa la
recuperación. Las métricas son Python puro, sin dependencias, y corren en CI —
así que son instantáneas y nunca pueden desviarse en silencio. Dados los chunk
ids recuperados en orden de ranking y el conjunto de ids relevantes, las métricas
de ranking clave son:

**Mean Reciprocal Rank** — cómo de arriba aparece el primer acierto:

$$
\text{MRR} = \frac{1}{N}\sum_{q=1}^{N} \frac{1}{\text{rank}_q}
$$

**nDCG@k** con relevancia binaria — premia los aciertos *y* su posición,
normalizado contra el orden ideal:

$$
\text{DCG@k} = \sum_{i=1}^{k} \frac{\mathbb{1}[\,\text{rel}_i\,]}{\log_2(i+1)}
\qquad
\text{nDCG@k} = \frac{\text{DCG@k}}{\text{IDCG@k}}
$$

```python
def ndcg_at_k(ranked_ids, relevant_ids, k):
    relevant = set(relevant_ids)
    dcg = sum(
        1.0 / math.log2(i + 1)
        for i, cid in enumerate(ranked_ids[:k], start=1)
        if cid in relevant
    )
    ideal_hits = min(len(relevant), k)
    idcg = sum(1.0 / math.log2(i + 1) for i in range(1, ideal_hits + 1))
    return dcg / idcg if idcg else 0.0
```

Junto a estas están recall@k, precision@k y hit-rate@k. Recall y hit-rate te
dicen *si* se encontró la respuesta; MRR y nDCG te dicen *cómo de bien se
ordenó*. La distinción importa: un sistema puede saturar el recall (encontrarlo
todo) y aun así mejorar ordenando el pasaje correcto más arriba — que es
exactamente lo que ocurre después.

### Preguntas gold vs. silver

El conjunto de confianza son 20 preguntas curadas a mano, cada una mapeada al
chunk que la responde — el conjunto *gold*, la fuente de verdad. Para escalar la
medición sin etiquetar miles a mano, un generador pide a un LLM que escriba una
pregunta autocontenida anclada en un chunk muestreado, descarta las deícticas o
triviales, y conserva solo las respuestas que un LLM-juez califica como fieles a
su fuente — un conjunto *silver* más grande.

Las preguntas sintéticas pueden favorecer al sistema que las generó, así que los
dos niveles **siempre se reportan por separado** y el gold sigue siendo
autoritativo. Ser honesto sobre los límites de tu propia medición es parte del
contrato.

### La línea base

La foto del «antes»: un modelo de embeddings multilingüe estándar
(`intfloat/multilingual-e5-small`), recuperación solo densa, corpus 2024 (2.225
chunks, 20 preguntas).

| Recall@10 | Hit rate@10 | MRR | nDCG@10 |
|---|---|---|---|
| 0.900 | 0.900 | 0.749 | 0.783 |

Cada cambio posterior se mide contra esta fila.

## Recuperación híbrida: dos maneras de equivocarse

La recuperación densa y la dispersa fallan de forma distinta, y los fallos son
casi complementarios:

- **Densa** (embeddings) capta el *significado* — ideal para paráfrasis, débil
  con tokens exactos raros como `Ley 39/2015` o `artículo 14`.
- **BM25** (léxica) capta los *términos* — acierta referencias exactas, ciega a
  los sinónimos.

Así que el sistema ejecuta ambas y las fusiona. La pata dispersa es un Okapi
BM25 en Python puro sobre un índice invertido — lo bastante ligero para correr en
CI:

$$
\text{score}(q, d) = \sum_{t \in q} \text{IDF}(t)\cdot
\frac{f(t,d)\,(k_1 + 1)}{f(t,d) + k_1\!\left(1 - b + b\,\dfrac{|d|}{\text{avgdl}}\right)}
$$

con $k_1 = 1.5$, $b = 0.75$ y un IDF suavizado
$\text{IDF}(t) = \ln\!\left(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\right)$. El
tokenizador es deliberadamente simple y determinista — minúsculas, separar en
límites no alfanuméricos, conservar acentos españoles y `ñ`, descartar una
pequeña lista de stopwords — porque tanto el corpus como las preguntas están bien
acentuados.

### Fusionar rankings, no puntuaciones

El truco para combinar dos recuperadores *no* es sumar sus puntuaciones — viven
en escalas incomparables. **Reciprocal Rank Fusion** combina los *rankings* en su
lugar, así que no hace falta normalizar:

$$
\text{RRF}(d) = \sum_{r \in R} \frac{1}{k_{\text{rrf}} + \text{rank}_r(d)}
$$

```python
def reciprocal_rank_fusion(rankings, k_rrf=60):
    fused = {}
    for ranking in rankings:
        for rank, chunk_id in enumerate(ranking, start=1):
            fused[chunk_id] = fused.get(chunk_id, 0.0) + 1.0 / (k_rrf + rank)
    return sorted(fused.items(), key=lambda kv: kv[1], reverse=True)
```

La constante de amortiguación $k_{\text{rrf}} = 60$ (Cormack et al., 2009) aplana
la influencia de los primeros puestos, de modo que un chunk bien rankeado por
*cualquiera* de las patas emerge en el resultado fusionado. Cada pata propone un
pool de candidatos; RRF los mezcla.

| Recuperador | Recall@10 | MRR | nDCG@10 |
|---|---|---|---|
| densa (baseline) | 0.900 | 0.749 | 0.783 |
| BM25 | 0.900 | 0.732 | 0.773 |
| **híbrida (RRF)** | **0.900** | **0.763** | **0.793** |

El recall no cambia — está clavado en un techo que marcan dos preguntas difíciles
que ambas patas fallan — pero la híbrida gana en las dos métricas de ranking (MRR
+0.014, nDCG +0.010). Modesto, honesto, y apuntando directamente al siguiente
problema: esas dos preguntas necesitan una señal de relevancia más fina.

## Reordenación con cross-encoder: rompiendo el techo

Un bi-encoder (el recuperador denso) embebe la consulta y cada pasaje de forma
*independiente* y luego compara vectores — rápido, pero solo puede aproximar cómo
de bien encajan. Un **cross-encoder** lee la consulta y un pasaje *juntos* y
puntúa la relevancia directamente. Mucho más fino, mucho más lento para correrlo
sobre todo el corpus. La respuesta estándar es una tubería de dos etapas:
recuperar un pool pequeño de forma barata, y luego reordenar solo ese pool.

El diseño mantiene el modelo pesado detrás de un `Protocol`, para que la lógica
de la tubería siga siendo testeable y sin modelo:

```python
class Reranker(Protocol):
    def rerank(self, query, candidates):  # candidates: (chunk_id, text)
        """Devuelve los candidatos como (chunk_id, score), mejor primero."""
        ...

class RerankingRetriever:
    def search(self, query, k=10):
        pool = max(self._pool, k)                       # p. ej. 30 candidatos
        candidates = self._base.search(query, pool)
        pairs = [(cid, self._id_to_text[cid]) for cid, _ in candidates]
        return self._reranker.rerank(query, pairs)[:k]
```

La híbrida recupera un pool de 30 candidatos, y luego
`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` lo reordena (~1,5 s/consulta en
CPU):

| Recuperador | Recall@10 | MRR | nDCG@10 |
|---|---|---|---|
| densa (baseline) | 0.900 | 0.749 | 0.783 |
| híbrida (RRF) | 0.900 | 0.763 | 0.793 |
| **híbrida + cross-encoder** | **1.000** | **0.888** | **0.913** |

Este es el resultado satisfactorio. Las dos preguntas difíciles *estaban* en el
pool de candidatos todo el tiempo — la recuperación las había encontrado, el
ranking las había enterrado. Leer la consulta y el pasaje juntos las promueve al
top 10, rompiendo el techo de recall **0.900 → 1.000**, con **MRR +0.125 y nDCG
+0.120** sobre la híbrida. El diagnóstico anterior («necesitan una señal más
fina») era correcto, y el arreglo está medido, no asumido.

## Validando la afirmación sobre el troceado

De vuelta a la decisión de troceado. El troceado a nivel de artículo *debería*
superar a las alternativas — pero «debería» no es una medición. Así que el corpus
se re-trocea de tres formas y se puntúa a **granularidad de documento** (un
acierto = cualquier chunk del documento relevante), para que estrategias con
límites distintos se comparen de forma justa:

| Estrategia | Recall@10 | MRR | nDCG@10 |
|---|---|---|---|
| **artículo (actual)** | 1.000 | **0.975** | **0.982** |
| tamaño fijo (1000/150) | 1.000 | 0.912 | 0.935 |
| documento completo | 1.000 | 0.975 | 0.982 |

Todo se encuentra a esta escala, pero el ranking los separa: **las ventanas de
tamaño fijo rankean el documento correcto más abajo (MRR −0.063)** porque
fragmentan artículos a mitad de idea. El nivel de artículo iguala la calidad de
ranking del documento completo — *y*, a diferencia de este, soporta de forma
única las citas exactas de artículo. La elección de producción se sostiene bajo
medición, y ahora puedo afirmarlo con una tabla en vez de una corazonada.

## Generación: citar, o rechazar

Hecha la recuperación, el trabajo del generador es responder **únicamente** desde
los pasajes recuperados, citarlos como `[n]`, y rechazar cuando la respuesta no
está. El system prompt es explícito sobre la cadena de rechazo, lo que hace los
rechazos detectables aguas abajo:

```python
REFUSAL = "No tengo información suficiente para responder."
# ... el system prompt instruye: responder SOLO desde los pasajes, citar fuentes
# como [n], y si la respuesta no aparece, responder exactamente con REFUSAL.
```

Para medir la calidad de respuesta sin un humano en el bucle, un **LLM-como-juez**
puntúa cada respuesta en dos ejes, cada uno una sola llamada que devuelve una
puntuación 0–1 más una breve justificación a `temperature=0` por estabilidad:

- **Fidelidad** — ¿está la respuesta anclada *solo* en los pasajes recuperados?
- **Corrección** — ¿coincide de verdad con la respuesta de referencia?

| Fidelidad media | Corrección media | Tasa de rechazo |
|---|---|---|
| 0.990 | 0.895 | 0.050 |

La fidelidad casi perfecta confirma que el prompt citar-o-rechazar rara vez
alucina. La corrección en 0.895 es el margen honesto — el número que el trabajo
futuro de recuperación y generación tiene que mover.

### Una capa de proveedor que sobrevive al tier gratuito

Juzgar y generar consumen muchas llamadas a LLM, y los tiers gratuitos limitan
con dureza. Así que los proveedores se sitúan detrás de un `Protocol` agnóstico al
fabricante, y un `FallbackProvider` los encadena con un **circuit breaker basado
en tiempo**: un proveedor con rate limit se omite durante una ventana de
enfriamiento en vez de machacarlo, pero se recupera después.

```python
except LLMRateLimitError as err:
    self._ready_at[provider.name] = time.monotonic() + self._cooldown
    rate_limited = True            # omite este proveedor, prueba el siguiente
# ...
if rate_limited and not other_error:
    # todos los proveedores enfriándose — lanza un tipo de error *distinto* para
    # que un llamador de larga duración pueda esperar y reintentar en vez de morir.
    raise LLMRateLimitError("all providers rate-limited -> " + detail)
```

El tipo de error distinto es el detalle que importa: un trabajo de evaluación
masivo puede distinguir «sin cuota, espera y reintenta» de «roto de verdad» y
actuar en consecuencia. Decisiones de infraestructura como esta son las que
permiten ejecutar el conjunto de evaluación con la frecuencia suficiente para que
sea útil.

## Servicio: compuesto a partir de las piezas medidas, testeable sin GPU

La tubería de consulta se compone detrás de un único protocolo `Engine` —
recuperar → opcionalmente reordenar → generar — y se sirve con FastAPI
(`/health`, `/search`, `/ask`). Como la capa HTTP depende del *protocolo*, no del
engine concreto, la API se testea con un fake trivial: **sin modelos, sin API
keys en CI**.

```python
class Engine(Protocol):
    @property
    def num_chunks(self) -> int: ...
    def search(self, query: str, k: int = 10) -> list[Source]: ...
    def answer(self, query: str, k: int = 5) -> AnswerResponse: ...
```

El mismo engine respalda una UI de chat en Gradio montada en la misma app, de
modo que la demo y la API JSON nunca pueden divergir. Cuando el tier del LLM está
limitado, `/ask` degrada con elegancia devolviendo los pasajes recuperados en vez
de fallar — y `/search` nunca necesitó un LLM en primer lugar.

Es la misma idea de separación de responsabilidades que los protocolos `Reranker`
y `LLMProvider`: mantén las cosas caras y no deterministas detrás de interfaces, y
la lógica a su alrededor sigue siendo rápida de testear y barata de razonar.

## Qué compraron las mediciones

Cada número destacado se remonta a una decisión que se ganó su sitio:

- **Troceado sensible a la estructura** — +0,063 MRR sobre ventanas de tamaño
  fijo, más citas exactas *gratis*.
- **Recuperación híbrida** — +0,014 MRR / +0,010 nDCG sobre la densa sola.
- **Reordenación con cross-encoder** — recall 0,900 → **1,000**, +0,125 MRR.
- **Generación citar-o-rechazar** — 0,990 de fidelidad, 0,050 de tasa de rechazo.

Ninguna de estas se tomó por fe. El arnés de evaluación es el héroe silencioso del
proyecto: es lo que convierte «esto parece mejor» en «esto *es* mejor, en esta
medida, sobre estas preguntas» — y lo que mantendrá honestos también los próximos
cambios.

## Qué viene

El sistema está **en producción en un Hugging Face Space público** (FastAPI +
Gradio, respuestas citadas), con una verja de regresión de evaluación en CI y
trazado opcional con Langfuse ya integrados. La hoja de ruta sigue condicionada a
la medición: afinar un modelo de embeddings jurídico-español (y demostrar que
supera a la línea base estándar sobre el mismo conjunto), añadir validación de
citas al generador, ampliar el corpus más allá de 2024 y montar una ingesta
incremental programada para que el índice siga el ritmo de cada nuevo número del
BOE.
